# コート・ボールの 3D 解析（試作）

固定カメラの試合動画から、コートの位置合わせ → ボール追跡 → サーブの落下地点・球速を出す試作。
IMG_0131（iPhone 14 Pro、1920×1080・約 60fps、地面から約 0.7m・手前ベースラインの約 6m 後ろ）で作った。

## 手順

```bash
# 1. 背景（選手のいない中央値画像）を作って白線を検出
python3 lines.py bg.png c                 # c_segs.npy, c_lines.png
python3 court.py c_segs.npy bg.png lines.json
python3 homog.py lines.json bg.png court_fit.png      # 地面の射影変換 (court_fit.png.H.npy)
python3 camera.py court_fit.png.H.npy cam.npz          # 焦点距離・カメラ位置
python3 refine.py cam.npz court_fit.png.H.npy cam3.npz 505 8   # ネットポスト・ネット中央・奥のベースラインで補正
# 2. サーブ 1 本（打球音の時刻を渡す）
python3 serve.py video.mov cam3.npz x 527.63
```

## しくみ

- **位置合わせ**: 白線（細く明るい線）を Hough 変換で拾い、ベースライン・サービスライン・サイドラインを識別して射影変換を求める。
  主点＝画像中心・正方画素として焦点距離とカメラ位置を出し、ネットポスト（高さ 1.07m）・ネット中央（0.914m）・
  奥のベースラインの行で補正する（`refine.py` の画像座標は IMG_0131 で読み取った値）
- **ボール**: 3 フレーム差分の小さな黄色い塊（選手の大きな動きの近くは除く）を、ほぼ等加速度でつながる点列として追跡
- **サーブ**: 打球音の時刻を打点とし、空中の点列に重力・空気抵抗つきの 3D 軌道を当てはめ、地面 (z=0) まで延長して落下地点とする。
  打点は「手前ベースラインの少し後ろ・高さ約 2.6m」を弱い事前条件にしている

## 精度と課題

- カメラが低い（ネットより低い）ので、奥のコートは数画素に圧縮される（奥のベースラインで 1 画素 ≒ 0.8m）。
  奥行きは軌道全体の当てはめで補うが、位置合わせの数画素の誤差で 1〜2m ずれうる
- 打点付近は選手の体と重なってボールを拾えないことが多く、14 本中 5 本しか軌道が取れなかった
- 実際の落下地点（正解）との照合はまだ。高さ 2〜3m から撮った動画なら精度は大きく上がる

## 公開データでの検証（TrackNet テニスデータセット）

TrackNet の論文著者が公開しているテニスのデータ（放送映像 10 試合・約 2 万フレーム、各フレームのボール位置と
打球・バウンドのラベル付き、https://github.com/yastrebksv/TrackNet の Google Drive）で検証した。

- `refine_court.py`: コートの 4 隅をおおまかに渡すと、全ての白線を当てはめて射影変換とカメラを求める。
  game1 で交点 20 個・最大誤差 1.3 画素（カメラは高さ 8.6m・手前ベースラインの 21m 後ろ）
- `eval_tn.py`: 「空中の軌道に 3D を当てはめて地面まで延長」した落下地点を、ラベルのバウンド位置と比べる。
  時間の刻みを補正すると（下記）、game1 の約 30 バウンドで左右 0.2m・前後 1.8〜2.8m（中央値）。
  放送の高いカメラでも前後は数 m ずれるので、落下地点はバウンドの瞬間を映像で捉えて求める必要がある
- 注意: このデータは 1 フレーム = 1/30 秒として当てはめると重力が約 17m/s² になり、実際の時間刻みは約 23fps 相当。
  game3 には 6 フレームごとの重複（25→30fps 変換）がある。`FPS=22.7 python3 eval_tn.py ...` で補正して評価した
- 自作のボール検出（差分＋つなぎ）は放送映像で再現率 28%・適合率 6% と不十分。公開されている学習済み TrackNet の重みを使う予定

## 学習済み TrackNet での解析動画（完成形）

自作の検出では、手前の選手のラケット（ボールと同じ蛍光黄色）を誤って拾う。学習済み TrackNet
（https://github.com/yastrebksv/TrackNet の model_best.pt。`tnet.py` に同じ構造を書き、重みだけを `weights_only=True` で読む）に置き換えると、
IMG_0131 でもトスからバウンド（V 字）・リターンまで途切れずに追える。

- `tn_run.py`: 1920×1080 の中央 1280×720 を 30fps・640×360 にしてボール位置を出す（Mac の GPU があれば MPS を使う）
- `tn_post.py`: 外れ値除去 → 画像上の V 字をバウンドとして地面の座標へ → サーブは「打球音の時刻＋打点の事前条件＋観測したバウンド地点」で 3D 軌道を当てはめて速度を出す
- `render.py`: ボールの軌跡・バウンドの輪・着地点の図・サーブ速度を重ねた動画を作る（当てはめ誤差 3 画素以上の速度は表示しない）
- `make_video.py`: 上をまとめて実行する

```bash
pip install torch opencv-python numpy scipy pillow
python3 make_video.py IMG_0131.MOV data/IMG_0131_cam.npz model_best.pt out --start 190
# → out/final.mp4（試合部分の全ポイント）
```

CPU（4 コア）では 1 フレーム約 3.5 秒かかり、試合全体（約 2 万フレーム）は 20 時間以上かかる。Apple シリコンの GPU なら大幅に速い見込み。
試作で 6 ポイントを処理した結果: サーブの着地点は 17.5〜19.0m（サービスライン 18.3m 付近）、速度 135〜141km/h。
奥側の着地点は位置合わせの誤差で ±1m 程度ずれうるので、イン・アウトの判定には使えない。

## 試合全体の解析（IMG_0131、2026-11-03）

- 音で見つけた 56 区間すべてを TrackNet（ボール周辺だけを見る `tn_roi.py`、CPU 4 コアで約 7 時間）で処理し、
  `tn_post.py` で 40 ポイントに組み立てた（試合部分 21 分 → 約 6 分）
- ポイントの組み立て（`tn_post.py` と `cut/rally.js` は同じ方法。`node test_rally.js` で一致を確認できる）
  - サーブ: 手前の選手は「大きな打球音 → 高い所から奥へ速く下りる球」。奥の選手は「手前のサービスボックス付近へ平均 60km/h 以上・
    ベースラインで打点 1.8m 以上」か「手前のサービスボックスに落ちて手前の選手が 1 秒以内に打ち返す」。
    どちらも直前 4 秒は手前の選手の打球もコート内（ベースラインから 1.5〜20m）のバウンドもないこと
  - フォルト: 同じ選手が 30 秒以内にまたサーブし、サーブが入った箱から見て同じ側から打っていればセカンドサーブ（違う側なら次のポイント）。
    側が分からなければ「返球されず（4.5 秒以内の打球音が 2 回未満）25 秒以内にまたサーブ」か「15 秒以内にまたサーブ」
  - 映像で確認: 42 本のサーブ（フォルト 7 本を含む）は、手前の選手の 25 本すべてでサーブの瞬間、奥の選手の 17 本も
    手前の選手がリターンの構え（奥は暗くてサーバーの動作は見えない）
- 結果: 手前の選手 20 ポイント（1st 75%）、奥の選手 19 ポイント（1st 84%）。サーブ速度の目安は手前 117〜163km/h、奥 128〜183km/h
- 取りこぼし: 22:55〜23:20 のラリーなど（サーブのバウンドも音も取れなかったもの）
